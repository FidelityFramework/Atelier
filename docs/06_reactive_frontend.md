# 06 - Reactive Frontend: Fickl, Ranvier and WREN

WREN applications use a WebView or browser as a visual surface and can connect that surface to native Clef services. **While the frontend is F# compiled to JavaScript, the selected compiler is Fickl and the selected reactive model is Ranvier.** BAREWire supplies shared typed encoding across its supported JavaScript, .NET and native Clef paths. Xantham supplies generated F# bindings to the selected web APIs and libraries. Each host supplies the WebView integration and platform services needed by that deployment.

Atelier is the in-house example for an editor, graph visualizer and compiler-services client. The same arrangement should support independently packaged applications with their own data and behavior. It can also run in a regular browser when the required data and services are available there.

This chapter sets the frontend contract and integration plan. WrenHello demonstrates a Linux WebKitGTK host and an earlier F#/Fable frontend. The chosen Fickl/Ranvier migration, integrated BAREWire transport and Atelier implementation require their own acceptance evidence.

## The frontend's place in WREN

```text
F# application frontend
  → Fickl → JavaScript
      → Ranvier state and effects
      → typed web API bindings generated by Xantham
      → browser or embedded WebView
              ↕
        BAREWire protocol and admitted transport
              ↕
        native Clef host and platform bindings
```

A browser-only visual can use data already available to it. A browser with a remote service adds an explicitly secured network boundary. A desktop or mobile application with a local backplane needs a host, native package and platform integration for each target. A shared frontend avoids maintaining a different visual application for every host; it does not make a platform-specific native binary universal.

The native host performs admitted platform operations and connects the frontend to application services. Farscape-generated bindings describe the native foreign interfaces that a particular host uses. Xantham-generated bindings describe JavaScript-facing APIs. The application communicates across these execution contexts through a defined protocol. A JavaScript object and a native resource handle have separate identities and lifetimes unless an explicit boundary contract connects them.

## Ranvier: state, derived work and effects

Use signals for current state, memos for derived values, and effects for work that must respond to changes. Keep event occurrences, commands and completions distinct from state snapshots. A list selection, its labels and a chart's data should be derived from the same admitted update when the application presents them together.

Ranvier's documented primitives illustrate the shape of the model:

```fsharp
// Ranvier's documented F# shape; pin and validate the selected Fickl build.
open Ranvier

use graph = new Graph ()

graph.Run (fun () ->
    let count = createSignal 1
    let doubled = createMemo (fun _ -> count.Value * 2)
    createEffect (fun () -> printfn "doubled = %d" doubled.Value)
    count.Value <- 5)
```

This small example illustrates the relationship among a signal, a derived value and an effect. It does not establish an editor, a browser renderer or a passing Fickl integration. Ranvier documents Fable/JavaScript support and tests its compiled engine under Node. Package versions, compiler options, browser APIs and the actual WebView remain separate gates. See [Ranvier's Fable target](https://ranvier-org.github.io/Ranvier/fable/) and [Ranvier documentation](https://ranvier-org.github.io/Ranvier/).

### Coherent updates

A received message is first decoded and validated against its schema, bounds and version. Apply the accepted changes as one appropriate reactive batch so that dependent views do not observe a half-applied update. A visual snapshot can then associate its values, labels, selection and graph or dataset revision.

For an accounting chart, the exact amount and currency remain in the model. A renderer can derive a bounded display coordinate under a declared conversion policy. Its label or accessible value comes from the exact amount for the same record and revision. For Atelier, a graph view similarly preserves the selected graph object's identity, relationship and actual proof status. Layout and animation are presentation work and do not create compiler facts.

A batch does not order messages across a network or make GPU work synchronous. A protocol must define snapshot revisions, ordered deltas and recovery when a delta's base is unavailable. An application may explicitly permit a newer complete snapshot to replace an older unpresented one. Commands, resource completions and structural deltas require their own delivery rules.

### Scope and cleanup

An editor window, document, component or visualization needs an explicit owner for subscriptions, effects and temporary resources. Ranvier documents owner scopes and cleanup when those scopes are disposed. The integration should connect that ownership to browser event listeners, workers, pending requests and any renderer resources it creates. See [Ranvier roots and owners](https://ranvier-org.github.io/Ranvier/guide/roots/).

Disposal and cancellation have different meanings. A request to stop work does not establish that a worker or GPU has stopped using its buffers. Late completion must be checked against the relevant document, view and device generation before it is accepted. GPU buffer retirement follows the actual completion contract; it is not guaranteed merely because a component stopped observing it.

### JavaScript target behavior

Ranvier's JavaScript documentation records target-specific details including single-threaded graph dispatch, promise delivery, equality cutoffs and unavailable .NET-only APIs. Treat that documentation as a guide to the tested Fable path. Confirm the selected Fickl output and options against the application scenarios instead of assuming every behavior is identical across compilers or hosts.

This matters for an editor: an equality policy determines whether a derived update is propagated, while a stale-result check determines whether an asynchronous result still belongs to the current document. A structurally equal value does not automatically identify the same request or resource. Bind identity and revision where those distinctions matter.

## The current WrenHello baseline

WrenHello's existing example uses F#/Partas.Solid compiled through Fable and a Linux x86-64 WebKitGTK host compiled by Composer. Its typed counter commands and events use a compact ASCII script-message channel. The inbound binding records UTF-8 length and rejects messages larger than 4,096 bytes before copying. The application documents BAREWire over a localhost WebSocket as the intended later transport.

That baseline supplies a concrete host, callback and lifecycle path to compare. The WREN direction in this chapter is Fickl and Ranvier. Migration needs an actual compiled frontend and an integration test with the native host. A retained frontend library or component needs an explicit adapter that preserves the selected state, event, batching and disposal behavior. No Solid-specific reactive runtime is a requirement of the selected design.

BAREWire's existing multi-target encoding, decoding, schema and framing are the foundation for the shared protocol. WrenHello needs to bind the selected shared codec and framing to its transport and exercise the endpoints, authentication or origin policy where relevant, bounds, shutdown and error handling together. The current bounded script-message bridge is not automatically a high-volume graph or GPU data channel. See [WrenHello](../../WrenHello/README.md) for its current host and bridge.

## Editor capabilities and browser components

The frontend needs a text editor, docking or layout, diagnostics, navigation, search, terminal output and visual inspection. CodeMirror 6 and Dockview are candidates for editor and panel behavior. Generate or establish F# bindings for the selected APIs, then build a small Ranvier integration around their actual event and disposal behavior. Their use should not depend on a Solid-specific wrapper when the underlying library and selected integration can provide the required operation directly.

For each component, establish:

- how document changes become events and how programmatic updates avoid feedback loops;
- how a document version associates diagnostics, selection and navigation with the text being shown;
- how a component is mounted, focused, detached and disposed;
- how editor, terminal and panel state survive or intentionally reset when a view is recreated; and
- how keyboard interaction, assistive technology, localization and platform input methods are supported.

Clef compiler facts come from the admitted CCS/Baker and Lattice interfaces. A frontend parser can support coloring or responsive presentation, but it does not become a separate authority for source semantics. A browser-side graph layout likewise positions a projection without adding a compiler relationship or proving an obligation.

## D3, WebGPU and the renderer boundary

Xantham's original binding target was D3.js. Re-exercise the current D3 generator output for the layout, scale, curve and interaction operations the application needs. Treat coverage as a test result for the selected declarations and compiler pin. D3 computes presentation data; Canvas 2D, WebGL 2 or WebGPU can realize the selected view.

The proposed Fidelity.WebGPU library is the browser-facing WebGPU API generated through Xantham, with a separate authored layer for capability checks, buffer layout, checked conversion and resource lifetime. A renderer may consume a coherent Ranvier snapshot, retain GPU resources across frames and process camera movement locally. The native host need not receive a message for each draw call.

A renderer owner can coordinate revision and device generation while GPU and worker operations complete asynchronously. Its mailbox orders decisions; the GPU queue supplies separate execution and resource-completion rules. The shared graph and application data remain authoritative. [WREN bindings and WebGPU](14_wren_webgpu_bindings.md) and [visualization integrity](13_visualization_integrity.md) develop the binding and lifecycle contracts.

A frontend WebGPU canvas and native GPU compute are both available design paths when their hosts support them. An application can use native GPU computation for its own workload and send an admitted result to the frontend. Sharing a native GPU allocation directly with a WebView requires an explicit host-specific mechanism, ownership, synchronization and security contract. A generated JavaScript API binding does not itself provide native GPU interoperability or compile Clef code to WGSL.

## Deployment and later Clef frontend

The same frontend design should be exercised in a regular browser and in each target WebView. Linux WebKitGTK, Windows WebView2, Apple WKWebView and Android WebView have distinct host APIs, versions and lifecycle behavior. WebGPU additionally depends on a secure origin, adapter, device, features, limits and the GPU/driver combination. Test the embedded host rather than inferring availability from a related browser. Provide an explicit fallback or report an unavailable required capability.

Clef's JavaScript/JSIR and JSX direction is the later frontend target. As it matures, compare the same application contracts, protocol cases and realized behavior with the Fickl baseline. Xantham's Fable-oriented F# output and Ranvier's tested JavaScript behavior do not by themselves establish native Clef compilation, JSIR compatibility or proof preservation.

The eventual proof-bearing path can connect the source judgment, encoded data, frontend conversion and rendered or computed result to the delivered artifact. That requires stated assumptions and evidence for each boundary, including WebGPU and shader behavior where applicable. Successful type generation or a green source check is useful evidence for its own scope.

## Acceptance sequence

1. Pin Fickl, Ranvier, Xantham, declaration sources, npm assets and the tested host. Record the compiled frontend artifact and its dependencies.
2. Compile a small Ranvier frontend with Fickl. Exercise signals, memos, batching, async completion, equality policy and owner cleanup in a regular browser and the actual WrenHello WebView.
3. Exchange a bounded typed update with the native host through the available bridge. Integrate the existing BAREWire codec and framing with the selected WREN transport, then validate both endpoints, malformed input, size limits, revision matching and shutdown end to end.
4. Mount a selected editor and panel component with the Ranvier adapter. Test text versions, selection, diagnostics, focus and disposal under rapid updates and document replacement.
5. Use current Xantham D3 bindings and a minimal WebGPU surface in an application visual. Verify capability detection, a renderer lifecycle and a clear outcome when GPU access is unavailable.
6. Deliver an old async result after a newer document or graph revision, and again after renderer recreation. The current view must remain associated with the accepted revision and device generation.
7. Record startup, memory, update latency, frame pacing and input responsiveness for the named workload and hosts. Compare any Electron-based reference under the same conditions before claiming a performance advantage.

These are implementation targets, not test results. The [visualization roadmap](15_visualization_roadmap.md) supplies the wider graph, graphics and cross-platform acceptance matrix.
